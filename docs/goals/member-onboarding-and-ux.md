## 0. 给执行 agent 的工作指令

请基于本仓库继续实现本文目标，完成代码、迁移、CLI、GUI、部署模板、测试和使用文档。不得只完成静态界面、只补命令名称、只写计划，或仅用 Mock 通过证明真实系统已经可用。

### 0.1 开始前必须完成

1. 阅读仓库已有的 `AGENTS.md`（如存在）、`README.md`、`docs/handoff.md`、`docs/acceptance.md` 以及本文。
2. 运行 `git status --short`、`git log -5 --oneline`，记录真实基线。本文提交只用于说明设计背景，不要求回退到该提交。
3. 保留用户已有改动。不得覆盖无关文件、强行重置工作区或修改研究仓库。
4. 核对当前实现，区分“已满足”“部分满足”“待实现”，将结果记录到本轮实现报告。
5. 执行当前可用的基线测试，保存命令、结果和跳过原因。

### 0.2 执行原则

- 按第 15 节分阶段推进。普通工程取舍采用本文默认方案，记录必要决策后继续，不反复向用户确认已明确的需求。
- 遇到生产机权限、部署、破坏性操作或缺失的真实身份信息时，不自行猜测；完成所有不依赖这些条件的工作，并明确标记待授权部分。
- 不因为本地没有 GPU、Docker 或管理员权限而停止全部开发；仍须完成实现、可运行的验证脚本和本地可执行测试。
- 不把未执行的 Docker、真实 SSH、GPU、浏览器端到端测试记为通过。
- 新增依赖应尽量少，锁定版本。沿用 Python、SQLite、现有 CLI 和轻量 HTML/JS；不引入 Kubernetes、Redis、独立企业级 IAM 或前端大型构建链。
- 不自行推送远程、合并分支或部署。是否进行本地提交遵循仓库约定；提交不得混入密钥、真实地址和私人联系方式。

### 0.3 不得越过的授权边界

本文授权的是**本地开发与隔离测试**，不是对 example-gpu 的操作授权。

未经另行明确批准，不得：

- SSH 连接 example-gpu 进行所谓“顺手检查”；
- 安装服务、修改目标机账号、SSH、udev、配额或防火墙；
- 重启 Docker、NVIDIA 或目标机系统服务；
- 开启目标机 `deployment_allowed`、`vscode_enabled`、`file_transfer_enabled`；
- 创建、停止、迁移、删除真实训练容器，或终止真实成员会话；
- 执行会影响本地真实用户账号和 SSH 的测试。此类测试必须在专用 VM 或明确隔离的测试环境中执行。

## 1. 背景、目标与非目标

### 1.1 现有基础

设计参照版本已具有：个人 Linux 身份、SSH 受限入口、root Broker、Unix socket、SQLite、Docker 资源分配、到期回收、队列、CLI、本地 GUI 和开发容器/VS Code 接入代码。

本轮直接相关的现有落点：

- `login_wrapper.py`：白名单和拒绝输出；已认证但没有原始命令时进入 `menu`。
- `cli.py`：资源、队列、任务、菜单和本地工作站入口。
- `gui/server.py`、`gui/static/`：本地工作台与管理员页面。
- `identity.py`：内核 UID 与管理员组解析。
- `store.ensure_user()`：记录调用者；它不是成员资格审批机制。
- `members.py`、`members.toml`：公开展示资料，不是授权依据。
- `deploy/create_user.sh`：账号、公钥和 workspace 配置。
- Broker 的 systemd unit：已有 `ProtectSystem=strict` 等限制。

以上是需要复用的基础，不是要求重写整套系统。源码依据见文末 [R1]—[R6]。

### 1.2 成功后的体验

**新成员**：打开入口 → 提交成员资格申请 → 查询结果 → 管理员批准并完成开户 → 本地配置向导 → 创建工作环境 → 进入终端或 VS Code。

**老成员**：继续使用熟悉的 SSH → 看懂迁移提示 → 进入菜单或本地工作台 → 继续已有工作或申请资源。

**管理员**：在管理面板处理申请 → 自动开通并看见结果 → 管理成员状态、公钥、有效期与限制 → 操作留痕。

**科研开发**：容器内安装系统包、调整依赖的自由度不因本轮 UX 改造缩减。已接受的取舍继续成立：容器、临时 HOME 和临时安装环境可销毁；`/workspace` 中的代码、数据和结果持久保留。

### 1.3 非目标

本轮不做 GPU 使用逐次人工审批、计费积分、多租户企业组织树、完整 SSO、邮件/短信平台、公共云管理门户、任意远程运维控制台或个人镜像构建平台。

不把“友好”理解为恢复共享账号、宿主机 shell、sudo、Docker socket 或无限资源权限。

不承诺阻止成员主动分享私钥或代他人使用账号。个人身份、公钥管理与审计能改善可追责性，但不能证明终端背后的自然人始终是本人。

| 编号 | 不变量 |

## 3. 面向用户的语言和信息结构

### 3.1 统一术语

面向成员默认使用中文；内部字段和兼容 CLI 参数可以继续保持英文。

| 技术术语 | 默认界面用语 |
|---|---|
| allocation | 工作环境 |
| apply | 创建工作环境 / 申请资源 |
| queued allocation | 等待资源 |
| membership request | 加入申请 / 成员资格申请 |
| pending review | 等待管理员审核 |
| shell | 终端 |
| release | 结束工作环境并释放资源 |
| job | 训练任务 |
| unmanaged | 未纳管任务（只读） |
| maintenance | 维护中，暂不接受新申请 |
| expired | 已到期，工作环境已结束 |
| cleanup_pending | 清理待重试，资源暂未释放 |

内部完整 ID、容器名、镜像 digest、原始错误码保留在“详细信息”中，并支持复制。不得只显示一个难以理解的 UUID。

### 3.2 成员工作台

默认只突出三个主区域：**开始/继续工作、我的任务与等待、资源与协作**。成员没有管理员权限时不显示管理员操作入口。

首页按状态呈现：

| 当前状态 | 首要操作 | 其次展示 |
|---|---|---|
| 尚未配置客户端 | 配置连接 / 申请加入 | 使用指南与管理员联系入口 |
| 申请待审核 | 查看申请进度 | 补充信息；不显示“GPU 正在排队” |
| 已批准但正在开户 | 查看开通进度 | 失败原因与重试状态 |
| 已启用、没有工作环境 | 创建工作环境 | 常用预设与空闲资源 |
| 一个运行中的工作环境 | 在 VS Code 中继续 / 进入终端 | 剩余时间、GPU、训练任务 |
| 多个运行中的工作环境 | 选择要进入的环境 | 名称、项目备注、资源、到期时间 |
| 正在等待资源 | 查看等待 / 取消 | 当前资源占用者；已运行环境仍可继续 |
| 暂停、过期、已撤销 | 查看原因和恢复方式 | 训练保留策略、数据保留说明 |
| 服务离线 | 重试 / 诊断 | 上次更新时间；不得把未知资源当空闲 |

申请页默认显示“用途/预设、GPU 数量、时长”，CPU、内存、具体卡号、镜像等收进高级选项。预设来自服务端配置，最终预算仍由 Broker 判断。

**GPU 数量必须和 GPU 编号分开。** 新增 `start --gpu-count 1` 代表申请一张卡；不得改变现有 `apply --gpus 3` 表示卡号 3 的含义。自动选卡必须在服务端准入过程中完成，不能由前端读一次空闲状态后自行认领。

### 3.3 工作流细节

- 创建成功后直接提供“进入终端 / 在 VS Code 中打开”，不要求用户复制 ID 再切到另一页。
- 可保存当前用户的常用预设；不得把上次配置当作服务端权限。
- 排队不是失败。显示等待原因和取消入口，不伪造无法保证的精确开始时间。
- 超时不等于创建失败。使用幂等键和操作 ID 查询原请求，不能重复点击就重复申请。
- 只有一个活动环境时，交互式 `connect`、`vscode` 可省略 ID；多个时给选择器。非交互模式遇到歧义必须报结构化错误，不能猜。
- 训练任务启动后展示日志与重新连接入口；不要把启动器退出成功说成训练已成功。
- 释放环境前明确提示：“训练将停止；临时安装环境和 HOME 会删除；/workspace 数据保留。”
- 原始错误在详细信息中保留，主提示必须说明发生了什么、当前状态和下一步。不得把 traceback 当默认用户反馈。
- 操作中禁用重复提交按钮；键盘可达、焦点可见，状态不能只依赖颜色。小屏可用但不追求复杂移动端功能。

## 4. 旧登录方式的引导与协议保护

### 4.1 先区分认证前与认证后

OpenSSH 的 `Banner` 用于认证前提示；`ForceCommand` 用于认证后的命令限制，两者不能互相替代。[R7]

| 场景 | 应有行为 | 不能做的事 |
|---|---|---|
| 使用已废弃共享账号/密码，认证失败 | 固定、简短的 SSH Banner 指向使用指南与申请入口 | 让旧凭据继续进入；泄露该账号是否存在或申请状态 |
| 合法成员 `ssh alias` 且有终端 | 状态感知菜单；有环境时突出继续工作 | 给宿主机 shell；只打印英文命令清单 |
| 合法成员直接执行 `bash`、`docker`、`nvidia-smi` 等宿主命令 | 拒绝执行，同时在 stderr 给对应的新方式 | 自动执行原命令；偷偷创建环境后执行 |
| 旧 scp/SFTP 客户端连宿主机 | 协议失败保持清晰；stderr 给受控传输/容器入口说明 | 往协议 stdout 填菜单；为兼容放开宿主机 SFTP |
| VS Code 直接连旧宿主目标 | 在可见诊断中说明应从 `citespec-resource vscode` 或 GUI 进入 | 自动识别任意 bootstrap 脚本并在 host 执行 |
| 合法 `--json`、tunnel、file 命令 | 保持现有协议和退出码；仅必要诊断去 stderr | 插入欢迎语、ANSI 控制符或交互提问 |
| 无 TTY、无明确命令 | 返回简短使用说明与适当非零状态，不等待菜单输入 | 在管道里永久挂起 |

SSH Banner 不保证所有客户端都会显示，因此同时提供实验室公告中的固定入口和可单独访问的使用指南。认证前信息必须是公开信息。

### 4.2 配置化提示

新增等价于以下的集中配置，真实值由管理员填写；这些是设计字段，不要求照抄名称：

```toml
[onboarding]
guide_url = "https://lab.example.invalid/compute"
apply_url = "https://lab.example.invalid/compute/join"
support_label = "实验室计算资源管理员"
support_contact = ""
legacy_login_notice_enabled = true
```

不得发布示例占位地址作为实际可用链接。未配置 URL 时显示诚实的管理员联系入口，并在部署预检中提示缺项。

建议认证前文案：

```text
本服务器已启用个人账号与限时工作环境，旧共享账号不再用于科研登录。
新使用方式：<guide_url>
申请个人账号：<apply_url>
已有账号：使用个人 SSH 密钥登录。
```

建议认证后拒绝文案：

```text
这条命令不能在宿主机直接执行；你的申请和数据没有被修改。

继续使用：
  直接 ssh <你的服务器别名>，打开资源菜单；
  或在你自己的电脑运行 citespec-resource gui。

进入已有环境后，可在容器内使用 sudo、安装软件和运行训练。
使用指南：<guide_url>
```

实际文案应根据命令类型减少无关信息。不要直接回显包含令牌、路径秘密或控制字符的完整原始命令。

### 4.3 菜单与工作站的边界

在服务器 SSH 会话中可以直接使用菜单，不需要成员先安装本地客户端。这是第一条最短可用路径。

在服务器中不得调用 `webbrowser.open()` 后声称已打开用户电脑的页面，也不得把服务器的 `127.0.0.1` 当作用户可以直接打开的地址。说明必须标注“在你自己的电脑运行”。

SSH Banner/配置安装须备份、dry-run、`sshd -t`、有效配置检查；保留独立管理员恢复通道。不得为了欢迎语修改其他管理员的认证策略。

## 5. 首次接入：从没有账号到能开始工作

### 5.1 第一版采用的闭环

实现一个**低权限的申请入口**，用于展示指南、接收加入申请、查询该申请的结果；管理员仍通过现有本地 GUI/CLI 审核。默认采用“邀请后可提交申请”，邀请只允许提交，绝不自动授予成员资格。

完整闭环必须在隔离开发环境可演示：

```text
管理员生成邀请
  → 新成员打开申请页或使用 join 向导
  → 提交姓名/归属/公钥等必要信息
  → 获取私有申请回执
  → 管理员核验并批准或拒绝
  → 批准后自动开户并验证
  → 申请人凭回执看到结果和自己的连接配置
  → 完成首次 SSH 认证
  → 自助创建工作环境
```

不要求接入邮件、短信或第三方身份平台。邀请可由管理员在已有实验室通信渠道发送。申请人可主动刷新状态，不得假装已发送不存在的通知。

### 5.2 最小申请字段

- 显示姓名、期望用户名、实验室归属或联系人、申请用途；
- 一种用于管理员核验的联系方式；
- SSH 公钥；
- 可选昵称；
- 是否同意公开某项协作联系方式，默认不公开；
- 使用约定确认：个人凭据不共享；资源有时限；临时环境可销毁；成果放 `/workspace`。

不默认收集学号、身份证、私人电话等无关信息。申请人自行填写的身份不是“已验证身份”；审核页必须区分自报信息与管理员核验记录。

**公钥不等于私钥。** 页面和 CLI 必须明确“只提交 `.pub` 公钥”。检测到私钥头、超长输入或非法密钥时立即拒绝，并提示误提交私钥者重新生成/撤销受影响凭据；服务日志不得记录其原文。

### 5.3 邀请、回执与隐私

- 邀请由管理员生成，使用高熵随机值、有效期、使用次数限制及撤销状态；服务端仅保存用于验证的摘要。
- 回执使用独立的高熵查询秘密；知道顺序编号或 request ID 不应能查询别人的申请。
- 默认单次邀请；提交重试使用幂等键，不能反复消耗邀请或生成重复申请。
- 限制请求大小、速率、待处理申请数量和公钥数量；给出友好但不泄露其他申请人的错误。
- URL、访问日志、审计、截图和 Git 中不能泄露邀请/查询秘密。若用一次性 URL 引导，应在交换后移除地址中的秘密，并配置适当的缓存和引用来源策略。
- 申请页只能查自己的状态和必要操作信息，不得返回完整成员表、GPU 占用、管理员凭据或私人审核备注。
- “拒绝原因”区分申请人可见说明和管理员内部备注。

### 5.4 本地配置向导

提供 `citespec-resource setup` 或等价入口，并让未配置的 GUI 首屏可进入它。客户端最小配置只需要连接目标/别名、个人用户名、所用密钥和信任信息；不要要求成员复制包含硬件预算和管理员策略的服务器 TOML。

向导应：

1. 检测本机 SSH、客户端版本，以及可选的 VS Code。
2. 选择已有 SSH 公钥；没有时提供生成新密钥的明确操作。
3. 不覆盖已有私钥，不把私钥上传到申请服务或服务器。
4. 读取管理员提供的连接信息；主机指纹从可信渠道核验，不能自动接受陌生主机或关闭主机密钥检查。
5. 将 SSH 配置写入受管理的独立片段，保留用户现有配置，支持 Windows 路径、并发和回滚。
6. 测试身份、服务可达性、成员状态与服务端 capabilities。
7. 成功后直接提供“创建工作环境 / 打开工作台”。

对于私钥口令、SSH agent 和没有 `code` CLI 的情况，分别给正确说明，不把它们统一报成“服务器故障”。GUI 仅启动本地程序时，应说“已启动连接程序”；未经验证不能声称 IDE 已连通。

### 5.5 无网络申请服务时的后备路径

支持在本机生成仅包含公开申请资料的申请文件，由管理员在 GUI 导入或用 CLI 导入。导入与在线申请必须走同一验证、审批和开户逻辑。

此路径用于尚未部署 HTTPS 入口的实验室，也用于离线开发测试；**不能用它替代本轮应实现的在线提交/查询接口**。不把任意上传文件当脚本执行。

## 6. 成员资格的权威状态与权限检查

### 6.1 必须建立真正的成员记录

现有 `users` 表主要记录已出现的 UID/用户名/角色；`ensure_user()` 不得继续被误用成“自动授予合法成员资格”。[R3]

引入独立的权威成员记录或等价结构。至少包含：

```text
member_id（不可复用的内部身份 ID）
linux_uid、linux_username
status
valid_until（可空）
display_name、nickname
public_contact（显式公开）
private_contact（仅本人及授权管理员）
access_version
created_at、updated_at
```

建议成员状态：

```text
provisioning → active → suspended → active
                   ↘ expired
                   ↘ revoked

provisioning → provision_failed → provisioning
```

“申请被批准”不等于“账号已开通”；批准后仍可能 `provisioning` 或 `provision_failed`。

普通资源操作要求：

```text
身份可验证
AND 对应成员记录存在
AND status == active
AND 未超过 valid_until
AND 实际账号绑定仍一致
AND 本次操作满足所有资源与环境策略
```

管理员控制操作继续使用服务端可信管理员身份校验，不通过客户端显示状态决定。第一版复用现有管理员授权机制，不在成员界面提供授予宿主 sudo、docker 组或管理员组的功能。

### 6.2 检查位置

不能只在 SSH 登录或 `apply` 检查一次。至少覆盖：

- 普通 RPC 请求中需要权限的命令；
- 新 shell、任务启动、文件传输和 VS Code 隧道；
- 排队请求真正准入时；
- 开通、暂停、恢复和有效期变更的竞态；
- 已连接会话的续存授权；
- Broker 重启后的状态恢复。

排队者被暂停/撤销、资格过期、UID 被意外复用时，不能继续从队列获得资源。准入提交时核对成员版本/状态，避免检查后被撤权却仍创建环境。

允许未启用状态访问的内容仅限必要的自身状态、说明和恢复入口；不得因此开放普通资源查询、任务操作或其他成员数据。

### 6.3 有效期

资格过期不能仅依赖每日清理任务；每次授权根据 UTC 时间检查。

新工作环境的到期时间不得晚于成员资格到期时间。缩短资格有效期时，管理员必须看到已有训练受影响的情况，并明确选择处置方式，不得悄悄改成另一种策略。

### 6.4 保留安全登录限制

暂停或撤销成员时：

- 保持受限登录 shell 与 `citespec-members` 限制语义；
- 不能通过删除匹配组而让账号退回普通 shell；
- 不得自动回收 UID 给新成员，也不得让新成员继承旧 workspace；
- 未列入显式迁移/批准清单的历史 Linux 用户不能因“本来在组里”自动成为 active；
- 不使用用户名或可修改的显示名替代不可复用的内部身份关联。

## 7. 管理员面板与审批操作

### 7.1 管理员信息结构

管理员中心默认有四部分：

1. **加入申请**：待审核、待补充、已处理；支持批准、拒绝和补充信息请求。
2. **成员**：状态、有效期、公开资料、密钥指纹、当前环境与资源使用；支持暂停、恢复、撤销、管理公钥和常规限制。
3. **资源与异常**：复用已有资源/任务管理；危险操作保留确认与原因。
4. **操作记录**：按成员、申请、操作和操作者查询。

默认显示待处理事项，而不是先展示 Broker 技术配置。禁止仅隐藏按钮就视为完成权限控制。

### 7.2 批准申请

审批详情至少展示：

- 申请人自报资料、核验记录；
- 期望用户名及冲突情况；
- SSH 公钥类型与指纹，不默认铺开整段密钥；
- 拟授予的成员有效期及常规资源限制；
- 将执行的开户步骤；
- 不会授予宿主管理员权限的说明。

批准必须携带申请版本或内容摘要。管理员预览后，若申请内容被修改，须重新确认，不能静默批准另一份公钥或用户名。

管理员核验可以通过现有实验室沟通渠道完成；记录“核验人、时间、说明”。不要把持有邀请或填写实验室邮箱自动等同于身份已核验。

### 7.3 并发与重复操作

同一申请被两名管理员同时处理，必须只有一个最终决策成功；另一方收到可理解的状态冲突提示。

同一批准请求重试不能创建第二个 Linux 用户、重复安装 key 或重复分配 workspace。已拒绝申请不得在没有新决策记录的情况下被旧异步任务重新激活。

推荐请求状态：

```text
pending_review → needs_info → pending_review
pending_review → approved
pending_review → rejected
pending_review / needs_info → cancelled
```

申请状态与开户 operation 状态分开。界面分别显示“已批准，正在开户”“开户失败，可重试”“已开通”。

### 7.4 成员操作的明确语义

| 操作 | 默认结果 | 对已有训练的影响 |
|---|---|---|
| 暂停交互访问 | 禁止新申请/新任务/新连接，取消未准入队列，关闭交互及传输连接 | 默认保留当前后台训练至原租期结束 |
| 恢复成员 | 重新启用资格；验证账号、公钥、配额状态 | 不复活旧队列、旧连接或已结束容器 |
| 到期 | 不再允许新使用；显示续期申请/联系入口 | 新建环境的期限本就不应超过资格期限 |
| 撤销资格 | 阻止后续使用并撤销登录凭据 | 默认保留 workspace；现有训练的继续/停止必须明确选择 |
| 紧急阻断并停止任务 | 立即拒绝访问，关闭会话，停止该成员受管环境 | 会停止训练；必须二次确认、填写原因 |
| 调整配额 | 修改未来准入限制并显示当前超额状态 | 默认不杀已有任务；追溯执行需单独确认 |
| 删除数据 | **不属于第一版默认成员操作** | 不提供一键删人同时 `rm -rf workspace` |

“暂停交互但保留训练”并不撤销已经运行的容器程序的全部能力；页面必须把这一取舍说清楚。怀疑凭据泄露或恶意程序时应选择紧急阻断，而不是普通暂停。

不得让普通管理界面暂停/删除最后一个恢复管理员。对受保护管理员账号的变更应拒绝并指向独立运维流程；不能让成员管理面板变成宿主机管理员授权中心。

## 8. 开户、修改公钥和撤权：必须可恢复

### 8.1 开户是持久化 operation

建议按以下顺序执行，并记录每步结果：

```text
冻结已批准申请内容
  → 校验用户名、公钥和目标策略
  → 为该申请保留唯一的成员/操作 ID
  → 创建或显式关联受控 Linux 账号
  → 配置受限 shell 和允许的组
  → 创建个人 workspace，设置并查询验证项目配额
  → 配置 root 管理的登录公钥
  → 验证账号、认证入口、组、路径、配额与权限
  → 激活成员资格
  → 更新申请结果与连接说明
```

激活前，成员不得获得资源使用权限。中途失败应保持受限/未激活状态，保留操作 ID、失败阶段和重试入口。

不要默认把现有同名 Linux 用户收编，也不要自动调整陌生账号 UID、HOME、shell 或已有目录权限。同名冲突进入显式处理；只有经过管理员确认的迁移清单才允许关联。

SQLite、`/etc/passwd`、公钥文件、配额和 workspace 不能构成一个普通数据库事务。使用操作日志、幂等步骤和重新核对实际状态的恢复机制。失败回滚不得删除已经存在的科研数据。

### 8.2 不得破坏 Broker 的 systemd 防护

现有 Broker 的 `ProtectSystem=strict` 与 HOME 只读等限制，意味着“Broker 是 root”不等于可以随意修改账号文件。[R5][R8]

**默认架构**：增加一个职责很窄的 root-owned 开通/撤权执行器，使用受控 systemd oneshot 或单一 worker；由 Broker 提交经过验证的操作记录。不要仅为开户把 Broker 的文件系统防护整体关掉。

执行器要求：

- 只处理固定操作类型，如创建受限成员、更新中央公钥、验证配额、撤销成员会话；
- 请求入口仅对 Broker/受信任管理员可用；
- 不接受任意 shell、命令路径、HOME、组、UID、systemd unit 名或宿主文件路径；
- 不执行申请人提交的脚本、JSON 中的命令字符串或带 shell 展开的参数；
- 使用固定程序路径和参数数组、输入白名单、超时及输出上限；
- 对文件操作采用已验证的路径与安全写入方式；
- 拒绝操作 root、系统服务用户、恢复管理员或未纳管账号；
- 安全步骤完成后才标记 operation 成功；
- 重启后可继续检查并收敛到确定结果；
- 原 `create_user.sh` 可保留为管理员入口，但应逐步复用同一底层逻辑，避免两套开户规则。

精确 unit/IPC 方式可由 agent 根据仓库选择，但必须写一份短决策记录，解释为什么不扩大现有 Broker 的权限范围。

### 8.3 公钥管理

成员可在已认证的会话中查看自己的 key 指纹、添加新 key、撤销旧 key。新 key 必须经过格式验证；建议要求新设备完成持有证明或试登录，再建议删除旧 key。

- 成员只能管理自己的 key；管理他人 key 必须有管理员权限和审计。
- 禁止把公钥输入中的 `command=`、`environment=`、来源限制片段等原样当作授权选项安装。
- 第一版只接收明确支持的普通公钥类型；证书或复杂 authorized_keys 语法不做隐式兼容。
- 不允许已登记给另一成员的同一 key 静默再次绑定；特殊情况进入管理员显式决策。
- 最后一个 key 的移除必须给出锁定风险并要求确认/恢复方案。
- 丢失全部 key 的人走管理员恢复，不提供凭姓名、邮箱字符串直接重置的后门。
- 容器 SSH 的授权 key 应从当前权威成员 key 集生成，不继续无限合并已撤销历史 key。

推荐用 root 管理的中央授权文件或等价的受控 `AuthorizedKeysCommand`，防止用户自行重建被撤销的登录入口；必须核对实际 sshd 生效配置及其他认证来源。[R7]

### 8.4 撤权要覆盖旧连接

修改数据库或移除公钥只影响部分路径，不能据此宣称已撤销全部访问。

暂停、撤销和紧急 key 撤销需要：

1. 先改变权威访问状态/版本，使后续 Broker 操作立即被拒绝。
2. 取消尚未准入的申请；正在准入的请求也要重新核对成员版本。
3. 关闭该成员的 shell、VS Code 隧道和正在进行的文件传输。上传中断不得留下替换一半的正式文件。
4. 处理真实 SSH transport 会话，防止旧 `ControlMaster` 继续开启新的通道。
5. 更新宿主机认证来源及容器 key 投影；移除 key 但无法精确识别其会话时，保守关闭该成员全部交互会话并告知用户。
6. 仅在管理员明确选择紧急停机时停止受管训练环境。
7. 验证结果并记录，不把“数据库已更新”显示成“全部撤权已完成”。

终止 SSH 会话必须定位受管成员及对应会话，不能接受任意 PID/UID，也不能误杀管理员或其他用户。逻辑撤权完成但系统凭据同步失败时，保持拒绝资源访问，界面显示“访问已阻止，凭据撤销待重试”。

已认证连接也必须受服务端状态约束；新加入的 `shell`、`file`、`tunnel` 特殊入口不能绕过统一授权检查。

## 9. 公共申请入口与现有系统的连接方式

### 9.1 默认架构

```text
未开户申请人
    │ 浏览器 / 本地 join
    ▼
HTTPS 申请入口（独立低权限 intake）
    │ 只保存申请、邀请验证摘要和申请结果投影
    │ 不持有 Docker socket，不接入成员 Broker socket
    ▼
管理员本地 GUI → 管理员 CLI → 已认证 SSH → Broker
                                          │
                                          ├─ 校验管理员权限、冻结审批内容
                                          ├─ 写入权威成员状态与 operation
                                          ▼
                                  狭窄的特权开通执行器
                                          │
                                          ▼
                              Linux 账号 / 公钥 / workspace / 配额

已启用成员
    本地 GUI/CLI → 已认证 SSH → Broker → 受控开发容器
```

继续沿用“成员/管理员的资源业务由 CLI 和 Broker 统一实现”。公共申请页是**尚未有 SSH 账号的人使用的受限接入通道**，不是新的资源 API。

### 9.2 intake 的权限限制

- 使用独立非 root 系统身份，不能属于 `citespec-cli`、`docker`、`sudo` 或管理员组。
- 只能访问自己的申请存储；不能写 Broker 的成员、allocation、配置、审计数据库。
- 生产默认仅绑定 loopback，通过已有 HTTPS 反向代理暴露；优先限制在实验室网络/VPN。开发可在本机 loopback HTTP 演示，但文档必须标注差异。
- 暴露的公开操作仅限：显示指南、验证邀请并提交申请、凭私有回执查询/补充/取消该申请。
- 公开入口不得包含批准、拒绝、开户、角色修改、资源分配或任意文件上传接口。
- 不得简单把当前管理员 GUI 改为 `0.0.0.0` 并称为申请系统。
- 若 intake 通过受限本地 IPC 与 Broker 同步，只能让 Broker 主动读取申请并提交结果；外部请求不能借此触发特权操作。
- intake 的数据一律视为不可信输入。审批时重新验证字段，并核对管理员确认过的版本/摘要。

默认沿用 Python 与 SQLite；不为此新增消息队列或通用工作流平台。公开申请服务与特权执行器的隔离是权限边界，不是要求做微服务体系。

### 9.3 唯一事实来源

- **申请资料**由 intake 保存；管理员审批时复制经确认的不可变快照到权威操作记录。
- **是否有计算资格**只由 Broker 的权威成员记录决定。
- **操作执行结果**由持久化 operation 决定；intake 显示的“已开通”是其结果投影。
- 不因 intake 状态被篡改、服务中断或消息重复而自动开启成员资格。
- 更新投影失败时允许重试，不撤销已经安全完成的开户，也不虚报申请结果。
- 离线导入同样生成申请快照，不能直跳为 active 用户。

## 10. 数据、迁移与审计

### 10.1 建议的最小数据实体

允许沿用现有数据库或拆分合适模块，但必须保证上节的权限边界。

| 实体 | 必需内容 |
|---|---|
| membership application | ID、版本/摘要、资料、公钥指纹、状态、审核人、公开结果、内部备注、时间 |
| member | 不可复用 member ID、Linux 绑定、权威状态、有效期、资料、访问版本 |
| member key | key ID、公钥、指纹、所属成员、状态、验证/撤销时间 |
| membership operation | operation ID、幂等键、目标成员、动作、冻结输入、阶段、状态、重试与错误 |
| invitation / receipt | 摘要、范围、有效期、使用状态；不记录可直接使用的明文秘密 |
| membership audit event | actor、target、action、时间、结果、原因、operation ID、脱敏差异 |

不要把私钥、邀请码明文或申请查询秘密写入事件详情。

`members.toml` 现有公开资料可以迁入新结构，但必须指定一个权威来源。建议 SQLite 成为可编辑资料的来源，TOML 作为一次性导入/导出兼容；不能长期两边写入造成姓名/状态不同步。

### 10.2 数据库迁移

- 实现版本化迁移；不能只创建新表或修改 `PRAGMA user_version` 就声称完成。
- 迁移前备份；支持中断后重试或明确失败，不损坏现有 allocation、GPU claim、队列和审计。
- 导入历史成员必须有 dry-run、显式批准列表及冲突报告。
- 观察到的 `users`、未知 Linux 用户、旧共享用户不得自动批量激活。
- 在成员迁移未完成时可保持 maintenance：停止新分配，继续安全回收已有租期。
- 操作系统中已存在的用户或目录不得被隐式删除、改 UID 或改归属。
- 新安装默认启用成员状态约束；升级不能靠永久关闭约束来保持表面兼容。

### 10.3 审计与隐私

所有批准、拒绝、补充信息请求、开户、失败、重试、暂停、恢复、撤销、公钥变更、限制修改和紧急停机均须留痕。

界面只向有权者展示私人资料。普通资源看板继续只展示已同意公开的姓名/昵称/联系方式。导出和故障包必须脱敏；测试夹具不得使用真实申请人信息。

保存周期应可配置。清理过期邀请和申请时，不删除必须保留的成员绑定与操作审计，也不删除科研数据。

## 11. CLI 与协议合同

以下是**拟实现接口示例**，不是当前版本已经支持的命令。可调整命名，但需在实现开始时固定最终命令表，保持一致并为旧接口保留兼容。

### 11.1 成员与首次接入

```bash
# 没有服务器账号也可使用；邀请秘密由安全提示输入，不放命令行参数。
citespec-resource join --portal https://lab.example.invalid/compute
citespec-resource join status

# 已批准后配置工作站。
citespec-resource setup --server example-gpu
citespec-resource doctor
citespec-resource me

# 普通工作路径。
citespec-resource start --gpu-count 1 --preset standard --open vscode
citespec-resource connect
citespec-resource vscode
citespec-resource gui

# 个人公钥。
citespec-resource me keys list
citespec-resource me keys add ~/.ssh/id_ed25519_new.pub
citespec-resource me keys revoke <key-id>
```

`join status` 的查询秘密由受保护的本地存储或交互输入提供，不能要求用户把秘密当作普通查询参数公开分享。

本地 `join/setup/start` 与远端白名单命令应明确区分。不要为支持本地便捷命令，把任意本地开程序能力暴露到宿主机 ForceCommand 中。

### 11.2 管理员

```bash
citespec-resource admin invitations create
citespec-resource admin requests list
citespec-resource admin requests show <request-id>
citespec-resource admin requests approve <request-id>
citespec-resource admin requests reject <request-id> --reason "身份尚无法核验"

citespec-resource admin members list
citespec-resource admin members show <member-id>
citespec-resource admin members suspend <member-id> --reason "暂时离组"
citespec-resource admin members resume <member-id>
citespec-resource admin members revoke <member-id> --reason "成员资格结束"

citespec-resource admin operations show <operation-id>
citespec-resource admin operations retry <operation-id>
```

危险操作默认交互确认；自动化调用必须显式确认并提供审计原因。参数不能直接映射成任意 shell 命令。

### 11.3 兼容与机器输出

- 保留现有 `apply --gpus`、`list`、`status`、`job`、`queue`、`release` 和既有 `admin users` 语义。
- 新增字段应兼容已有 JSON envelope；破坏性变化必须版本化，不得静默修改。
- `--json` stdout 只能输出约定的结构；人类说明在 stderr，默认不输出 ANSI。
- 非交互失败必须有非零退出码；不同业务状态使用稳定错误码。
- 建议结构化错误提供 `code`、`message`、`next_actions`、`operation_id` 等可选信息；GUI 渲染允许的动作类型，而不是执行任意服务端字符串。
- 在存在活动环境且未指定 ID 时，只有交互模式可以自动选择唯一环境；机器模式必须确定目标或给出明确错误。
- 创建/审批/开户等跨时长操作快速返回操作引用，后续查询状态。客户端超时不能触发重复创建或把已受理操作当失败重放。
- 持续字节流仍使用既有专用通道，不用 JSON 反复包装训练流量或破坏 SSH 数据流。

### 11.4 错误文案例子

```text
等待审核：
你的加入申请已提交，尚未获得服务器使用资格。
下一步：查看申请进度；无须重复提交。

资源不足：
目前没有符合条件的空闲 GPU，已进入资源等待队列。
下一步：保留等待、取消等待，或查看占用者的公开联系方式。

成员暂停：
你的交互访问已暂停。当前后台训练按管理员选择的策略处理。
原因：<可公开原因>
下一步：联系管理员申请恢复。

开户部分失败：
申请已批准，但 workspace 配额验证未完成。
尚未授予资源使用资格。管理员可对操作 <operation-id> 重试。
```

- 示例配置、依赖锁与 CI。

## 13. 必须处理的失败和竞态

以下不是可推迟的装饰性优化，而是成员管理闭环的一部分：

- 两个管理员同时批准/拒绝同一申请；
- 点击批准后 HTTP/SSH 断线，但后台已经创建 Linux 用户；
- 开户到任一步时进程退出、系统重启或磁盘写满；
- 同名用户/同名目录已存在，或者 UID 绑定与记录不一致；
- 重复申请、重复公钥、邀请码过期、回执泄露后的撤销；
- 申请内容在管理员预览后发生修改；
- 一个成员等待资源时被暂停，或排队准入与撤权同时发生；
- 旧 SSH ControlMaster、终端、文件流和 VS Code 隧道仍然连接；
- 公钥撤销后容器里仍残留旧 key；
- Broker/执行器/intake 任一不可达；
- 恢复操作被重复执行，或旧批准任务晚于撤销任务完成；
- 新增或修改成员限制后，旧客户端仍使用缓存策略；
- 提示信息污染机器协议；
- 自动选卡时并发申请同一组空闲卡；
- GUI 重复点击、客户端重试、命令超时造成重复资源占用。

业务状态必须单调且有条件更新，避免已撤销成员被迟到的开户任务“重新启用”。操作执行前和激活前均核对目标成员访问版本/期望状态。

## 14. 验收用例与证据

### 14.1 三条必须走通的主路径

**路径 A：老成员迁移**

合法成员用旧方式 SSH → 看见中文引导 → 无须本地安装即可进入服务器菜单 → 选择继续已有环境或创建新环境 → 在容器运行命令 → 找到本地 GUI/VS Code 新入口。

认证失败的旧共享凭据只能看到公开提示，不能进入菜单或创建任何状态。

**路径 B：新成员加入**

管理员生成邀请 → 无账号用户提交申请 → 用户得到私有回执 → 管理员在 GUI 审核 → 批准后自动开户与配额验证 → 用户查看到“已开通” → setup 完成主机信任与个人认证 → 创建环境并进入 VS Code/终端。

另走一次拒绝路径：拒绝后没有新 Linux 账号、key、workspace 资源承诺或计算资格。

**路径 C：管理员管理已有成员**

查看成员当前环境和 key → 普通暂停 → 队列取消、交互连接关闭、后台训练按选择保留 → 恢复后重新认证可用 → 撤销一把 key → 旧 SSH 复用通道不再可用 → 明确选择紧急停机时只停止该成员受管训练 → workspace 与其他成员保持完整。

### 14.2 可判定验收清单

所有测试使用虚构成员和独立测试环境；不得对真实成员和实验机执行以下破坏性步骤。

| ID | 场景 | 通过标准 |
|---|---|---|
| AC-01 | 旧凭据认证失败 | 可显示静态指南；不能得到 shell/菜单、成员状态或任何资源权限。 |
| AC-02 | 合法 SSH 无命令 | 有 TTY 时出现中文、状态相关菜单；无需记住 allocation ID。 |
| AC-03 | 非交互与协议 | JSON 可直接解析；文件字节逐字一致；SSH tunnel 不混入欢迎语；无 TTY 不挂起。 |
| AC-04 | 旧宿主命令 | 命令未执行，非零退出，stderr 给准确替代入口，不泄露原始命令中的秘密。 |
| AC-05 | 首次配置 | 不覆盖用户 SSH/私钥；陌生主机不静默信任；能处理错误口令/缺少 VS Code。 |
| AC-06 | 快捷创建 | 使用预设和 GPU 数量创建；并发申请不双分配；点击重试不多建环境。 |
| AC-07 | 多个环境 | 不猜测目标；交互选择清楚，机器模式遇到歧义返回可解析错误。 |
| AC-08 | 无账号申请 | 不需要成员 SSH 凭据即可按邀请提交；不能接触 Broker、Docker 或成员数据库。 |
| AC-09 | 申请隐私 | 随机猜 request ID 无法查询他人申请；token 不出现在日志/错误页。 |
| AC-10 | 申请输入 | 私钥、key 选项注入、用户名/path/命令注入、过大请求均拒绝，且无特权副作用。 |
| AC-11 | 审批并发 | 两个管理员并发操作只有一个决策生效；重复批准只有一个成员和一个开户链路。 |
| AC-12 | 审批内容变更 | 审批请求绑定版本/摘要；预览后资料变化必须重新确认。 |
| AC-13 | 开户端到端 | 正确的受限用户、公钥、workspace 和有效硬配额都验证后才 active。 |
| AC-14 | 开户失败恢复 | 每个阶段注入失败/重启均可安全重试；不会误删已有目录，不产生可越权半成品。 |
| AC-15 | 拒绝申请 | 不产生 Linux 用户、登录 key 或 active 成员；申请人仅见公开原因。 |
| AC-16 | 身份状态权威 | `ensure_user`、显示名修改、重新登录不能把 suspended/revoked 变回 active。 |
| AC-17 | 排队者被撤权 | 暂停/过期/撤销后不能准入；竞态下也不创建可使用的新环境。 |
| AC-18 | 旧连接撤权 | 已有 shell、VS Code、文件流及 SSH ControlMaster 均按策略失效，不只拒绝新连接。 |
| AC-19 | 普通暂停 | 禁交互和新申请，但后台训练按“保留至租期”选择继续；UI 明确告知。 |
| AC-20 | 紧急停机 | 二次确认与原因完整；只停止目标成员受管环境，其他任务和 workspace 不受影响。 |
| AC-21 | 恢复/过期 | 恢复不重放旧队列；实际时间过期即时阻止授权，不依赖周期任务。 |
| AC-22 | 公钥轮换 | 新 key 验证可用；撤销旧 key 后宿主与容器路径均不再接受；不误撤其他成员。 |
| AC-23 | 管理员边界 | 普通成员直调管理 API 被拒绝；不能把自己升级管理员或通过参数扩大宿主权限。 |
| AC-24 | 执行器边界 | 非授权 UID 无法调用；只能执行固定动作；Broker 原有防护未被整体关闭。 |
| AC-25 | 迁移旧数据 | 旧 DB 的资源/审计保留；未知账号不自动 active；UID/目录冲突不被隐式修复。 |
| AC-26 | 前端真实路径 | 实际浏览器点击完成提交/审核/状态/进入环境；不是只测静态 HTML 是否有某词。 |
| AC-27 | 兼容回归 | 原 CLI、JSON、队列、到期、`cleanup_pending`、文件与 GPU 预算测试不退化。 |
| AC-28 | 服务/网络失败 | 显示真实阶段；操作重试幂等；不把连接失败显示成申请拒绝或重复发起。 |
| AC-29 | 数据与环境生命周期 | 结束环境后临时软件/HOME 消失，workspace 保留；成员操作不暗中删除数据。 |
| AC-30 | 权限投影和恢复 | intake、Linux 公钥和权威记录不同步时不授予额外权限；能报告并重试收敛。 |

### 14.3 测试分层

**单元和业务测试**：状态机、幂等键、权限、时间边界、密钥解析、策略计算、内容版本和迁移。

**协议/服务集成测试**：真实 Unix socket 身份、独立低权限 intake、RPC、队列与撤权并发、失败恢复。测试实际入口，不只直接调用内部函数绕过认证。

**隔离系统测试**：在可销毁 Linux 环境运行真实 sshd、账号操作和 systemd/等价部署约束。覆盖公钥认证、受限 shell、中央 key 配置、ControlMaster、真实操作恢复。不能在开发者主系统直接造账号或改 SSH。

**浏览器测试**：运行真实 GUI/申请页，验证操作、错误和焦点；可以使用开发依赖中的 Playwright 或同等工具，不因此引入生产前端构建链。保留脱敏截图/测试输出。

**目标机验收**：GPU 设备隔离、真实配额、现有运行服务兼容和生产 VS Code 路径继续遵循实机验收流程。涉及主机状态变更的操作按维护窗口执行。

缺失工具时写清测试项、未执行原因和可执行命令；Mock 测试通过不能替代真实 sshd、Linux 用户、配额或浏览器验收。

## 15. 分阶段推进与退出条件

| 阶段 | 主要交付 | 阶段退出条件 |
|---|---|---|

可调整内部任务顺序，但不得把 M2 的授权缺口留给“以后再补”，也不得仅完成 M1 的文案就宣布整体 Goal 完成。

每阶段应新增相应测试并运行回归。版本控制遵循仓库约定，阶段记录应能定位到实际代码基线。

## 17. 完成定义：不要让“完成”含糊

### D1：实现完成、可进入隔离验收

必须全部满足：

- 本文第一版范围已有真实代码，无核心占位按钮或未实现命令；
- 旧登录迁移、成员资格审核、已有成员管理三条路径在应用层完整；
- 权威状态检查覆盖普通 RPC 和特殊流入口；
- 队列、公钥、会话、开户/撤权失败恢复均有测试；
- 本地可运行的测试与既有回归通过；
- 对必须在 Linux/真实 SSH/浏览器中验证的项目，已提供可运行测试而不是只有文字；
- 未执行项目显式标记，文档不宣传其已可生产使用。

### D2：隔离环境验证完成、可考虑受控试运行

D1 之外，必须有隔离 Linux 账号/真实 SSH/开通执行器、撤权及浏览器主路径证据。不存在阻断性错误；缺少依赖的 SKIP 不算通过。

如果本地环境无法执行 D2，报告写“D1 完成，D2 未覆盖”，并列出需要目标机/CI 补齐的项。

### D3：目标服务器可开放

D2 之外，还需要独立批准、旧权限回收、实机验收、GPU 与存储隔离、真实 VS Code 及恢复通道验收通过。

**D3 不在本文的默认执行授权范围内。** 不得通过开启配置开关或试探性部署来补证据。

### 完成后用户应看到的结果

成员可以：

> 申请加入 → 得到清楚的审核/开通状态 → 配置个人连接 → 创建或继续工作 → 用终端/VS Code 开发 → 结束环境且保留成果。

管理员可以：

> 查看申请 → 核验并批准/拒绝 → 看见开户实际结果 → 管理已有成员 → 安全暂停/恢复/撤销 → 查询操作记录。

这些行为应当是系统已经实现的工作流，不是 README 中的未来愿景。
